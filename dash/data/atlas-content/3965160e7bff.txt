# agent-architecture — Known Traps

> Agent design and operation traps: skill discovery, boot context, redundancy, system prompt behavior.

## TRAP — Skills need dual-path redundancy: Registry + SOPs, not just the skills-list scanner
**When:** Creating or deploying any pre-flight skill (context-triggered rather than keyword-triggered)

**Symptom:** A skill exists on disk and has trigger conditions in its metadata, but agents don't load it. The skill was created but didn't fire when relevant work came up — it was invisible to the agent despite being correctly installed.

**Cause:** The skill-matching mechanism in the system prompt scans available skills at turn start. This is a single point of failure — if the LLM scan misses a match, there's no fallback discovery path. Pre-flight skills (`load before ANY website change`, `load before ANY DNS change`) are especially vulnerable because they're context-triggered rather than keyword-triggered.

**Fix:** Dual-path redundancy for all pre-flight skills:
1. **Registry.md** — skill must appear under appropriate section
2. **SOPs.md** — skill must have an explicit MANDATORY section with trigger conditions and load order
3. **Self-lint** — weekly scan catches orphaned skills (skills not in Registry or SOPs)
4. **Same-session registration** — register new skills in both Registry and SOPs immediately on creation

On-demand skills with unambiguous keyword triggers (cold-email, copywriting) can rely on the skills-list scanner alone. Pre-flight skills MUST have dual-path coverage. A skill is only as reliable as its weakest discovery path.

## TRAP — Certify Before Complete: ATTEMPTED ≠ COMPLETED
**When:** An agent runs an automated workflow that changes business state (applies labels, updates statuses, writes CRM records) and marks the work "complete."

**Symptom:** Workflow exits without error but output is incomplete or incorrect — partial extractions, missing fields, zero-value records — and the agent silently propagates bad data downstream. The agent marked the work "done" when it was only "attempted." The label/stage was advanced before the output was verified.

**Cause:** No architectural gate between "process ran" and "mark complete." The agent conflates "the script exited" with "the job is done." Without mandatory verification, partial success presents as total success.

**Fix:** Insert a hard certification gate between execution and completion. Pattern: WRITE → READ BACK → VERIFY → CERTIFY → PROGRESS. Never: PROCESS RAN → DONE. Define required output fields, validate they exist and are non-trivial, and only then apply the completion marker. For any automation where business state is at stake, `CERTIFY BEFORE COMPLETE` is a permanent operating principle — not optional.

## TRAP — Initial Customer Email Law: Protocol Before Content (Never Draft from Memory)
**When:** An agent generates a customer-facing email or document from training memory instead of loading the canonical template first.

**Symptom:** Generated content violates mandatory elements of the approved template — wrong opening, missing identity introduction, wrong signature, missing required footers. QPaint Email 1: 7 of 14 mandatory elements violated because drafts were generated from memory rather than the canonical `qpaint-recovery-introduction` template.

**Fix:** Permanent Law: NO INITIAL CUSTOMER EMAIL MAY BE DRAFTED FROM MEMORY. Canonical template MUST be retrieved before content generation begins. Variable substitution only. Pattern: LOAD TEMPLATE → SUBSTITUTE VARIABLES → GENERATE → CERTIFY. Never: REMEMBER → GENERATE → SEND. This applies to all customer-facing content (emails, quotes, proposals, contracts), not just email.

## TRAP — Next Touchpoint Date ≠ Contact: "I'll be in touch" → review point
**When:** An automated agent processes a Next Touchpoint Date (NTP) field as a send/contact trigger for customer outreach.

**Symptom:** Agent auto-contacts a customer on their NTP date, but the customer had explicitly said "I'll be in touch soon." The date was a REVIEW point, not a CONTACT trigger — the agent contacted the customer when what was needed was internal review. This erodes trust and makes the agent look tone-deaf to customer signals.

**Cause:** Automation conflates a date field with a send trigger. Without an explicit REVIEW/CONTACT distinction on every scheduled touchpoint, any date that arrives becomes an implicit send instruction. The customer's clear signal ("I'll reach out when ready") is overridden by the cron firing.

**Fix:** Distinguish REVIEW from CONTACT on every scheduled touchpoint:
1. When customer says "I'll be in touch," preserve the commercial state (Engaged stays Engaged) — send only a brief acknowledgment (no CTA, no question, no promise to follow up on a specific date).
2. Set the next touchpoint as REVIEW ONLY, with First Action explicitly marked "REVIEW ONLY (not contact)" so no automation treats the date as a send trigger.
3. At review time, a human (or agent with context) evaluates the situation before deciding whether another contact is warranted. The date arrival is a signal to check in internally, not a signal to message the customer.

## TRAP — CRM stage is not commercial truth: customer evidence outranks system fields
**When:** Reconciling customer relationship records against primary evidence (emails, documents, calls)

**Symptom:** Agent treats CRM status fields (Contacted, Engaged, Lost, Won) as ground truth about the customer relationship, even when customer communications contradict the CRM state. A customer marked "Contacted" who has replied is still treated as cold. A customer marked "Lost" who reached out is missed. A customer left in an automated sequence despite QPaint managing them directly. The CRM reflects stale automation state or manual data entry, not commercial reality.

**Cause:** No architectural rule establishing that primary customer evidence outranks system fields. CRM fields are treated as authoritative because they are structured data with labels that sound like facts ("Contacted" = "contacted happened"). Without an explicit hierarchy where customer evidence > any system field, agents default to trusting the schema over the signal.

**Fix:** Establish as a permanent operating principle: primary customer evidence (emails, calls, signed contracts, documents) outranks any CRM status field. Before acting on a status field, verify against actual customer signals. If the CRM says "Contacted" but the customer replied, the customer reply governs. If the CRM says "Lost" but there is no customer evidence of loss, the state is unresolved. Pattern: LOAD CUSTOMER SIGNALS → COMPARE WITH CRM FIELD → if conflict, CUSTOMER SIGNAL WINS → UPDATE CRM TO MATCH. Never: USE CRM FIELD AS TRUTH.

## TRAP — Pre-Outbound Relationship Scan: check full relationship history before any customer contact
**When:** An agent prepares to send any customer-facing outbound communication (email, phone call, follow-up).

**Symptom:** Customer replies with confusion or irritation — "I already spoke to James," "You already sent me a quote," "I replied yesterday" — because the agent sent an unrelated follow-up from a different mailbox or department track. The agent had no awareness of the customer's existing relationship with a colleague or other part of the business.

**Cause:** The pre-outbound review checked only one mailbox (or one CRM record) while the customer had an active conversation with the business through a different channel. Underlying cause: no architectural requirement to scan the full customer relationship — multiple quotes, prior replies/conversations across all mailboxes, Won work, and any colleague-managed threads — before initiating contact.

**Evidence from field:**
- Vivien Lennan (14 Aug): Received Email 2 while already in a james@ conversation. "Responded to James yesterday" — reply flagged the disconnect.
- Dean Baker (QBuild): 3 quote records across Caboolture/Kallangur/Tullawong. One human with three quotes — not three independent customers.
- Nicholas Zappacosta: Won Logan Village + open Beenleigh quote. An Email 1 touch while he is already a Won customer would damage the relationship.

**Fix:** Before any customer outbound, the agent MUST:
1. **Scan all business mailboxes** the customer could have contacted, not just the sending mailbox. If the customer speaks to a colleague via a different email identity, that conversation is part of the relationship.
2. **Check for multiple quote records** belonging to the same human/business. One person with 3 quotes = one relationship, not 3 prospects.
3. **Check for Won work** — a Won customer who still has open quotes should not receive a cold Email 1.
4. **Check for prior conversations** — replies, opt-outs, complaints, requests — in any mailbox.

This belongs inside the **Customer Context Gate** (`communication_history_reviewed` step), not as a standalone workflow. The gate is the right architectural enforcement point: it runs before every outbound and must verify the full cross-mailbox relationship, not just the single record being actioned.

**Corollary — Tender/Government quotes are not customer follow-ups:** Formal tender submissions (e.g., QBuild specification quotes with 90-day validity, school-holiday timing) are procurement processes, not customer queries requiring "have you received your quote?" follow-up. Sending customer-relationship touches to a procurement officer damages the business's credibility. Distinguish: if the quote was submitted via a formal process to an organisation (not an individual), treat it as tender monitoring — not customer follow-up.

## TRAP — Data-Loss Through Import: Preserve Commercial Context
**When:** Performing any bulk data operation (import, re-import, migration, ETL) on customer records
**Symptom:** After a data re-import, contact data (name, email, quote value) survives but decision-critical commercial context is lost — quote date, scope, segment, relationship/source, procurement status, previous-client status, recovery score. Subsequent reviews then see historical quotes as "current" and government records as ordinary residential — producing wrong follow-up decisions.
**Fix:** Before/after any bulk data operation, verify these fields survive (or are intentionally excluded): 1) quote date, 2) scope/extent, 3) segment/customer type, 4) relationship/referral/source, 5) procurement/government status, 6) previous-client status, 7) communication history, 8) current commercial state. Pattern: BACKUP BEFORE IMPORT → VERIFY EACH FIELD → RESTORE IF MISSING.

## TRAP — Observation-Window Handoff: expiry must surface a review, not create a silent gap
**When:** An observation/waiting window on a customer record expires and no automated outbound is configured to fire
**Symptom:** An observation window (e.g., "wait 48h for quote review") expires with zero customer contact. The review-to-decide handoff never ran because autopilot outbound was disabled/retired. The expired window falls through a silent gap — no signal reaches the operator that a customer needs attention.
**Fix:** Standing rule: An observation window expiring MUST surface the customer for REVIEW → DECIDE. It must never mean automatic Email 1, and must never disappear because automated outbound is disabled. A disabled autopilot falls through to a human review signal, not a silent gap. Pattern: SET REVIEW REMINDER → WINDOW EXPIRES → SURFACE FOR REVIEW (with full context) → OPERATOR DECIDES.

## TRAP — Quote Intelligence Requires Commercial Context, Not Just Data
**When:** Evaluating or following up on a customer quote using only structured data fields (name, email, value, address, basic scope)
**Symptom:** Follow-up decisions are wrong because the agent lacks WHO/WHAT/relationship/decision-type/decision-makers/timing/differentiator context. A "Residential" label on a body-corporate complex changes the follow-up decision. Quotes with no phone number are marked "SOURCE UNAVAILABLE" rather than proceeding with available data.
**Fix:** Intelligence needs commercial context: 1) Customer Segment is commercially meaningful — a Residential label on a corporate complex changes approach. 2) Phone = SOURCE UNAVAILABLE (don't block on it — some templates don't have phone fields). 3) Correct segment where evidence clearly establishes it; do not infer from email domain alone. 4) Do not redesign CRM or intake infra — adapt to client's existing workflow and template.

## TRAP — Missing Data ≠ Automatic Hold
**When:** A customer record arrives with incomplete data — missing relationship context, ambiguous names, unknown segment — and the default instinct is to HOLD all communication until the gaps are filled.
**Symptom:** Two QPaint quotes at draft time had data gaps. Tom Clark: relationship context unknown (homeowner vs builder). Russ Dee: surname ambiguous ("Russ Dee" vs email "dunster"). Default instinct was to HOLD both. HOLD based on data incompleteness alone delays appropriate customer contact unnecessarily.
**Cause:** No materiality gate exists for data gaps. The system treats all missing data as equally blocking — gaps in data quality are conflated with gaps that affect commercial decision-making. Without a test for materiality, every gap becomes a stop.
**Fix:** HOLD only when the missing information is material to a safe or commercially appropriate contact decision. Apply the materiality test: "would knowing this change what we say, or whether it's safe to say anything?" Tom → material (builder vs homeowner changes framing) → resolved via primary evidence → reclassified Residential→Commercial, builder Email 1 sent. Russ → immaterial (first name source-verified, surname unneeded) → proceeded with "Hi Russ". UNKNOWN remains UNKNOWN, but UNKNOWN must not unnecessarily paralyse the journey.

## TRAP — Standing per-prospect instructions outrank general autonomy delegations
**When:** Operating under a general autonomy delegation (founder autonomy, tier-1 delegation, general latitude to decide next actions).
**Symptom:** A general autonomy directive tempts the agent to override a per-prospect standing instruction (e.g. "Monitor for reply. Do NOT chase. Founder call when he replies."). During Atlas's one-day founder autonomy test, Rahamed (Inspire Painting) was a candidate for persistence — but his specific per-prospect instruction correctly won. Sending another email would have violated the standing protocol and undermined the founder-call strategy.
**Cause:** Autonomy delegations grant general latitude to decide the next action. But per-prospect protocols (standing instructions, "do not chase" rules, escalation boundaries, specific contact windows) are specific, deliberate decisions that must not be overridden by a general directive. Without an explicit hierarchy, proximity to general autonomy tempts the agent into treating per-prospect constraints as optional.
**Fix:** Establish a clear hierarchy: per-prospect standing instructions ALWAYS outrank general autonomy. Before acting under any autonomy delegation:
1. Check if a per-prospect standing instruction constrains the decision.
2. If a per-prospect instruction exists and conflicts with the autonomy directive, per-prospect wins.
3. Autonomy ≠ the right to override every standing protocol — it is the right to decide within the boundaries already set.
4. Document each autonomy grant with explicit mention of which per-prospect instructions are preserved.

## TRAP — Dream classifier false positive: inline API calls ≠ skill regression
**When:** The nightly dream/consolidation classifier evaluates agent tool-call logs and recommends skill changes based on observed patterns

**Symptom:** The dream classifier flags "N hand-rolled `urllib.request` calls this week despite the `<domain>-api` skill" and recommends wrapping operations as helpers — but the calls are legitimate: they match the skill's own documented invocation pattern. `execute_code` is blocked in cron mode so standalone `/tmp/*.py` + terminal runs are mandatory by design. The classifier conflates "I see `urllib.request`" with "the skill is being ignored," when in fact the skill's recipe IS `urllib.request`.

**Cause:** Two conflation errors:
1. The classifier reads `urllib.request` + `.env` sourcing as "hand-rolled" but for skills that are documented API recipes (not importable libraries), this IS the canonical pattern.
2. The classifier counts all `urllib` entries without checking which host/service they target — ORGO/harvest/Gmail patterns get lumped with the domain under review.

**Fix:** Treat a `urllib` call as a regression ONLY if it diverges from the skill's documented recipe (wrong endpoint, wrong field, missing verification step). Merely seeing `urllib.request` + `.env` is not evidence. Before actioning an "inline API call" recommendation:
1. Run `grep -c urllib.request logs/tool-calls.jsonl` for the real total
2. Classify hosts (orgo/asana/gmail/docs vs truly uncovered ops)
3. Check the skill's own invocation section — if the "inline" pattern matches it, the recommendation is a false positive
4. Document the correction in the skill's Operational Pitfalls section so future dream runs see it

**Prevention:** When authoring skills that operate in cron mode (where `execute_code` is blocked by `cron_mode: approve`), make the canonical invocation pattern explicit in the SKILL.md so the dream classifier can distinguish intentional design from regression.
## TRAP — `is_failure()` keyword-match: "EXCEPTIONS: none" / "0 exceptions" marks SUCCEEDING cron jobs as failures
**When:** Running any cron or script that reports status with `is_failure()` keywording in log-retention or daily-summary scripts — particularly consolidation, founder-readiness, and inventory-pulse jobs that report "0 exceptions" or "EXCEPTIONS: none" as positive signals.

**Symptom:** False failure reports in `logs/daily-summaries/`. The `is_failure()` function keyword-matches the response section, so phrases like "EXCEPTIONS: none" and "0 exceptions" (intended as SUCCESS indicators) trigger the failure classifier. Jobs that completed perfectly — e.g., Overnight Founder Readiness (18/18 gates pass), QPaint Daily Attention (0 founder exceptions) — are marked FAILED in daily summaries. This causes unnecessary attention and incorrectly preserves large outputs for 90 days instead of 24h.

**Fix:** Fix the keyword-matching in `scripts/bin/log-retention.py` to exclude success indicators from failure detection:
1. Add an exception list of success phrases like "EXCEPTIONS: none", "0 exceptions", "no errors"
2. Before marking any failure, check the response section for these patterns
3. Cross-check: verify the daily-summary failure flag against the file's actual `## Response` text before escalating
4. The detection pattern: a daily summary shows a failure flag for a job that completed cleanly → first check the keyword match, not the job itself

## TRAP — Customer deferral ("still thinking / comparing") is MONITOR, not a courtesy reply
**When:** A prospect replies with a decision-deferral — "still thinking", "still deciding", "I'll let you know" — and the agent considers a same-day acknowledgement email.

**Symptom:** Three customers replying with deferrals were candidates for same-day acknowledgement emails. Two were left unanswered. None of the three asked for anything. A courtesy reply would have read as a nudge and risked the repetition the persistence decision exists to prevent.

**Cause:** A deferral is not an open loop: there is no blocker to uncover and no unanswered question. Treating a deferral as "engagement" invites exactly the repetition the persistence decision aims to prevent. A courtesy reply adds no value and reads as a nudge, eroding trust.

**Fix:** Classify as MONITOR — no acknowledgement email. Set `Next Touchpoint Date` to a review date tied to the quote's validity (or 14–21 days out), `Buying Stage at First Reply: "Still Deciding"`, `Primary Objection: "Timing"`. If the quote validity expires before the review date, surface the extension/requote question to the decision-owner at review time. A deferral is resolved by time, not by another message.

## TRAP — Engaged + external dependency = WAIT/MONITOR; detect acceptance from primary evidence
**When:** A prospect is engaged (has expressed interest or said "looks reasonable") but the blocker is an external dependency outside the business's control (third-party contractor, structural work, council approval, another vendor's process).

**Symptom:** The temptation with an engaged customer is more contact — follow-up emails, check-ins, nudges. When the blocker is external (e.g., "carpentry needs to happen before painting" — managed by a different company), repeated contact reads as pressure on a customer who has already said yes in principle. The business risks damaging the relationship by chasing when the customer has nothing new to tell them.

**Cause:** No architectural classification for "blocked but still engaged." Without a WAIT/MONITOR state, the automation or agent defaults to either (a) continuing normal follow-up cadence (wrong — customer already signalled intent) or (b) going silent without a review trigger (risks missing the external dependency resolution). The engaged-but-blocked state needs its own protocol.

**Fix:** For an engaged customer whose genuine blocker is external to the business:
1. Classify as **ENGAGED → WAIT/MONITOR** the external dependency.
2. Do NOT send follow-up nudges — a customer who has already said yes does not need a CTA. Brief acknowledgements only if the customer reaches out.
3. Set a review date (not a contact date) timed to the expected external dependency resolution.
4. **Detect acceptance from primary evidence** — the external party's completion notification, a signed contract from the partner, or the customer's direct signal. Do NOT rely on a CRM status change.
5. Reconcile as Won only when primary evidence confirms the contract/acceptance. Attribution discipline: if the customer signalled intent before any intervention, the win is Assisted, not Recovered.

**Standing rule:** A review date on an externally-blocked customer is a WAIT/MONITOR point, not a send trigger. "I'll be in touch when ready" from a customer who has already said yes is not a signal to chase — it is a signal to wait for the external dependency to resolve and monitor for the acceptance document.

## TRAP — Substring validation in certification gates: legitimate field content that happens to contain a blocked keyword fails the gate
**When:** Implementing or maintaining a certification gate that validates required fields using substring matching against a block list — particularly fields that may contain platform or vendor names as part of legitimate content.

**Symptom:** Certification gate fails with a specific field named even though that field is fully and correctly populated. Example: `certify_intake_complete()` returns `False, ['Extent of Work']` while read-back shows 924 characters of substantive scope text. The reconciliation gate passes but completeness fails. The signature: a field reads back as long and substantive, yet the gate says it is missing.

**Cause:** Blunt substring test in the validator — e.g. `"pandadoc" not in str(v).lower()` — intended to catch fields that are nothing but a raw platform link, but triggered by legitimate scope text that ends with "(PandaDoc expiry 13/10/2026)". The validator cannot distinguish "this field is nothing but a link" from "this field is substantive content that happens to name the platform."

**Fix:**
1. Recognise the signature: reconciliation PASSES, the read-back field is long and substantive, and the completeness gate names exactly that one field. That combination is a validator-pattern problem, not a data problem.
2. Reword the field value to remove the blocked keyword (e.g. "document expiry date 13/10/2026" instead of "PandaDoc expiry 13/10/2026"), PATCH the record, re-read, re-certify.
3. Never weaken or bypass the validator — a bypass converts a real control into decoration.
4. Never file the source email or advance the record while certification fails — filing makes a bad record unrecoverable.
5. Long-term fix: use a more precise validator pattern — check for a minimum content length AND the absence of platform-specific patterns, rather than a bare substring match against a blocklist.

**Source:** QPaint intake #43164 (2026-09-13). The field was 924 characters of legitimate scope. Certification failed because the text ended with "(PandaDoc expiry 13/10/2026)". Reworded, both gates passed.

## TRAP — A negative grep is evidence about the pattern, not about the thing (2026-09-18)
**When:** Concluding that a policy, rule, or convention does not exist because a keyword search returns nothing.
**Symptom:** A grep for three guessed patterns returns nothing and the negative result is recorded as "the rule does not exist". The rule exists under different vocabulary in several other files, and the false absence hardens through multiple artefacts (skill pitfall entry → daily note → founder decision) before anyone re-checks it, masking the real gap behind the wrong question. Seen 2026-09-18: "the no-weekend-send guard is not written down anywhere" was true of the guessed vocabulary only — the policy is documented as the "Weekend Send Prohibition" in three files.
**Fix:** A grep confirms what a pattern matches, never what does not exist. When searching for a known policy or convention: (1) search the concept and its documented phrasing, not just guessed keywords; (2) search the policy-owning skill as well as `knowledge/`; (3) run `git log -S <keyword>` before concluding absence; (4) if two or more phrasings return nothing, record "not found by these patterns" and name them explicitly — never record "does not exist"; (5) never let "rule does not exist" harden through multiple artefacts without an independent second search strategy. A registry that does not list something is evidence about the registry, not about the thing.

## TRAP — Weekly deltas are meaningless without the multi-week mean
**When:** Describing a week-on-week change in any low-volume metric (GA4 sessions, small-N business counts)
**Symptom:** The weekly website intelligence report showed "+100% sessions" week on week, which reads as growth. The prior week (6 sessions) was the quietest of 15 weeks — comparing two adjacent low-volume weeks produces large percentages that carry no information.
**Cause:** A single week-on-week ratio over a small denominator amplifies noise; there is no baseline for what "normal" is.
**Fix:** Before describing any week-on-week change as a rise or fall, pull the full period series (e.g. `isoYearIsoWeek` dimension) and compare the current week against the period mean. Recorded in `knowledge/website-intelligence-standard.md` under Structural findings. Applies to any low-volume metric, not just GA4.

## TRAP — A subagent's research summary is a self-report, not evidence
**When:** A subagent (flash/delegated child agent) produces research output with fabricated registration-style fields — a wrong ABN, a wrong owner name, unconfirmable email addresses — but its own summary reads as clean and complete with no flags. Fabrication surfaced only when the written data was checked against the sources.

**Source:** 2026-09-30
**Cause:** An LLM subagent fills a missing registration-style field with a plausible-looking value rather than null; the failure is silent in the child's own report.
**Fix:**
1. Never trust a subagent's summary self-report — verify the written data against the source; a child agent claiming "verified" is a self-report, not a fact.
2. For Australian business research: ABN Lookup `legalName` is the ground truth for sole-trader owners (`https://abr.business.gov.au/ABN/View?abn=<ABN>`, read `itemprop="legalName"`). For Pty Ltd / trust entities, ABN does not reveal the owner — use the site About page only where it explicitly names owner/founder/director, else null.
3. Never record an owner name from reviews or testimonials.
4. Do not run concurrent subagent batches against the same output files — this makes "which version is current" undecidable.

## TRAP — A prose gate in a record is not a gate: the send keyword outranks it (2026-10-03)
**When:** A record's `First Action` (or `Outreach Notes`) carries a founder/condition instruction written in prose, while the same field also contains the trigger keyword the automation fires on ("Begin follow-up sequence").
**Symptom:** The rule engine reads state plus a keyword; it does not parse the second sentence of a 600-character field. A record that says "do not contact until the founder rules" sends anyway, because the condition sits at the END of the paragraph behind the trigger keyword. Seen 2026-10-03: 3 of 13 Email 1 candidates carried founder conditions written after the "Begin follow-up sequence" clause.
**Fix:** A condition is not a control until it is at the FRONT of `First Action` and explicitly negates the trigger keyword; retain the original instruction verbatim in the field (auditability beats tidiness) and append a dated `Outreach Notes` line naming what supersedes what. Check the ORDER, not just the presence: "Begin follow-up sequence ... founder to confirm before Email 1" and "HOLD — founder to confirm before Email 1 ... [original] Begin follow-up sequence" carry the same words and opposite meanings. Fail closed — the cost of a guard is a possible one-day delay.
**Source:** `learnings/2026-10-03-prose-gate-not-a-gate.md`; Prepare-Ahead scan 2026-10-03 22:00 ACST.
