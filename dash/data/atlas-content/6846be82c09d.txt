# INC-2026-08-05-003 — atlas@ Lacked gmail.send Scope, Replies Silently Undelivered

**Incident ID:** INC-2026-08-05-003
**Date:** 2026-08-05
**Severity:** S1 — Customer Communication Failure
**Status:** Resolved — atlas@ re-authorised and independently verified

---

## Summary

Two QPaint customer replies (Arno Hsu — won deal, Kate Quinn — lost deal) were attempted from atlas@notforgotten.com.au. The Gmail API accepted both requests and returned HTTP 200 with message IDs. Neither email was delivered. The atlas@ OAuth token (`google_token.json`) was authorised for `gmail.modify` only — it lacked `gmail.send` scope. The API silently accepted send requests without the required permission.

Additionally, `quotes_token.json` has the same scope limitation.

Airtable was updated to reflect replies that were never sent — a protocol violation: Airtable was updated before delivery was independently verified.

## Root Cause Analysis

### Technical Root Cause

`google_token.json` was authorised via OAuth with `gmail.modify` scope only. The Gmail API send endpoint (`/users/me/messages/send`) accepted the request without `gmail.send` permission, returning HTTP 200 with a message ID that corresponded to a modify/draft operation rather than a delivered send. This is a silent failure — no error code, no rejection, just no delivery.

### Architectural Root Cause

The operating system allowed production communication to begin without first proving the production environment was capable of sending email. There was no Production Readiness Check to verify token scopes before attempting customer communication. The system trusted API success responses without independent verification of delivery.

### Protocol Violations

1. Evidence → Action (skipped Verification, Decision, Update)
2. Airtable updated before delivery verified
3. Incoming message IDs reported as outgoing IDs in verification report
4. Protocol broken twice in same day (QPaint replies + earlier white-label workflow)

## Learnings

1. **Never trust a send success response.** Independent delivery verification is mandatory.
2. **Production must prove it is healthy before operating.** This is not optional — it's a hard gate.
3. **Token scopes are production-critical configuration.** Scope gaps must be detected before sends, not after failures.
4. **Airtable must never be updated before delivery is independently verified.**
5. **The correct sequence is: Check → Communicate → Verify → Evidence → Airtable → HQ. Nothing may occur out of order.**
6. **API silent failures are the most dangerous kind.** The Gmail API's behaviour (accepting send without send scope) is a trap. We must guard against it.
