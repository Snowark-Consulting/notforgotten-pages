# Learnings Corruption — Incident Series Index

> Standing fact sheet for the recurring out-of-band corruption of `learnings/catalogue.md` and `learnings/cards/*.md`. Read this before investigating a new occurrence: the history is already here, and it has been misdiagnosed twice. Established 2026-09-20 (14th occurrence), per weekly vault-lint recommendation 7.2. Updated 2026-09-30 (22nd occurrence) — **the widest card damage since the 16th and the third consecutive re-injection of content a prior run had already rejected.** Four files in a 5.6 s burst (`catalogue.md`, `cards/qpaint.md`, `cards/gmail.md`, `cards/git.md`), guard = 29 findings. `cards/qpaint.md` — the live client's card and the boot-loaded routing target for QPaint work — was **cut from 12 `## TRAP` headings to 3** (9 lost outright or renamed with their dated evidence stripped); `cards/gmail.md` repeated the 24-headings-before-and-after pattern; `cards/git.md` had the autostash **discriminator stripped again** (the exact regression the 19th event's repair corrected) and carried a fabricated GH001/`tools/` block; `catalogue.md` lost its warning block and two rows. **Two re-injected blocks were rejected for the second time** (a foreign "15th occurrence" block and the `multipart/mixed` attachment trap already judged out-of-domain on the 21st). Two writer blocks passed attestation and were re-applied. See the occurrence log. Updated 2026-09-29 (21st occurrence) — the **reworded-heading class repeated** (`cards/gmail.md`: 24 `## TRAP` headings before *and* after, so only a heading **list** diff finds it) and the writer **re-injected the 20th event's rejected block** onto `cards/cron.md`, which failed attestation a second time; see the occurrence log. Updated 2026-09-27 (19th occurrence) — **file mtimes are evidence, not proof: the snapshot cron's `--autostash` rewrites the mtime of every dirty file, but a small burst across a few files is still a real write. Apply the discriminator in the Mtime-evidence row.** (17th occurrence, 2026-09-23: the clean-HEAD baseline was destroyed and the repair playbook changed.)

## Damage signature (stable across events)

- `catalogue.md`: `EDITING THIS TABLE` warning block deleted, one or more domain rows dropped, other rows `||`-prefixed, `campaign` cell rewritten as a markdown link, blank line inserted mid-table.
- Cards: whole `## TRAP` sections deleted; some bodies displaced under a neighbouring heading; occasionally a heading **renamed** (reads to the guard as a deleted trap).
- The writer also **adds**: its version usually carries 1–4 blocks, some genuinely new to the card layer, some condensed rewrites of traps it just deleted. **Attest every one before re-applying it** — do not treat its additions as real learnings by default.
  - 15th event (2026-09-21): added a macOS `arm64e.x1` linker trap that appears nowhere else on disk (no `LEARNINGS.md` entry, no dated file, no cron output, no session row) — NOT re-applied.

No such script on disk, no such job in `cron/jobs.json`, and `consolidation-sop.md` has no step 0.6. The writer is no longer only deleting real content — it is **fabricating infrastructure**. Verify any writer block that cites a path, job ID or document section against the filesystem before believing it.
  - **18th event (2026-09-26): carried a DUPLICATE of an existing series record.** Its `cards/gmail.md` version included a "Learnings corruption, 15th occurrence" block that is already held in full in this file and in `learnings/2026-09-21-learnings-corruption-15th.md`, and which does not belong in a Gmail card. The lesson: attestation catches fabrications, and the duplicate check catches a second, independent failure mode — both are required, in that order.
  - **17th event (2026-09-23): re-injected 4 blocks already judged unattested on the 16th** (two dream-cost false positives, the `memories/`-is-live-store block, a delegation block) plus a condensed copy of the 16th event's own record. Only the `memories/` block survived attestation — and it passed on **direct filesystem verification**, not provenance: `tools/memory_tool.py::get_memory_dir()` returns `get_hermes_home() / "memories"`, and the dir holds live `MEMORY.md` + `USER.md`. One block's central claim was **false on the day it was written** (it asserted `model.default` was `deepseek/deepseek-v4-flash-0731`; `config.yaml` says `deepseek-v4-pro`). **A writer block can be re-injected after a previous run already rejected it — re-run attestation every time; never inherit last night's verdict.**
- Burst pattern: files written 1.1–5.7 s apart = a loop over files.

## Repair playbook (do in this order)

1. **Pre-restore safety check.** `git diff --numstat` the whole tree first — other files may carry legitimate uncommitted work that a blanket `git restore` would discard. **A dirty `cards/*.md` is not automatically damage:** on the 20th event `cards/email.md` was dirty but was a real, independently-attested learning (verified against the source file and a skill reference), so it was deliberately **not** restored — attest a card's blocks before restoring it, or the repair destroys knowledge.
2. **Establish a clean baseline. Do NOT assume HEAD is clean.** (Changed 2026-09-23 — see Falsified #4.) Test HEAD first: `git show HEAD:learnings/catalogue.md` must contain the `EDITING THIS TABLE` marker with no `||` rows. If HEAD is corrupt or the history was re-initialised, recover a pre-write baseline from the old pack:
   ```bash
   # list every commit object incl. unreachable ones, then keep those not in rev-list --all
   git cat-file --batch-all-objects --batch-check='%(objecttype) %(objectname)'
   git show -s --format='%H %ct' <candidates>     # pick the newest by date
   git show <commit>:learnings/catalogue.md       # grep for 'EDITING THIS TABLE'
   ```
   Pick by **content marker, not commit date** — a fresh snapshot commit can carry the corruption.
3. **Restore the damaged files from that baseline** (full-file rewrite via `git show … > file`). **Never fuzzy-patch.**
4. **Extract** the writer's genuinely-new blocks from the working tree (copy them to `/tmp` before restoring).
5. **ATTEST each block — every run, from scratch.** Test: (a) is it named by a `## YYYY-MM-DD` entry in `LEARNINGS.md` or a dated `learnings/YYYY-MM-DD-*.md`? (b) does a `state.db` row predating the write carry it? (c) does a skill reference or another card state the same rule? (d) can the block's specific factual claims be verified against the filesystem today? If all four are no: **leave it out and record the non-action as a decision.** Re-apply only attested blocks, by appending (never fuzzy-patching).
6. **Duplicate-check** each attested block against `LEARNINGS.md`, the cards and the skill references before re-applying.
7. **Verify by heading LIST diff** against the baseline, not counts. A count passes cleanly when one trap is added and one deleted.
8. **Reconcile the catalogue bidirectionally**: every `cards/*.md` needs a row, every row needs a card, warning block present, zero `||` rows, no blank line inside the table.
9. Update the catalogue warning block and `memory/MEMORY.md` with the occurrence count and window.
10. **Commit the repair** (`git add learnings/ && git commit`) so the guard's HEAD-based diff has a correct baseline again — otherwise a correct repair reports as deletions.
11. **Re-run the guard as the LAST step** — its 21:20 cron cannot see work written after it.

## Falsified hypotheses — do not repeat

1. **"The guard ran before the write."** A UTC-mtime-read-as-Adelaide-local error. The write lands ~10 h *after* the guard.
2. **"The writer window contains no tool calls."** Occupancy varies: 13 unrelated `quotes-pulse-phase2` calls on 2026-09-14, zero on 2026-09-16. The constant is that none of them touch `learnings/`.
3. **"The 06:03 ACST window."** A one-hour UTC+09:30 slip; the window is ~07:03–07:08 ACST.
4. **"HEAD is a clean reference because the 21:30 backup committed the repaired file."** True for events 1–16, **false from the 17th (2026-09-23)**. Two independent reasons: (a) the hourly dashboard job runs `git add -A` with a hardcoded dateless message and had already committed the 07:06 corruption; (b) the vault backup was re-homed to `Hardstaff08/notforgotten-vault` at 08:50 ACST the same morning as a **fresh single-commit snapshot**, so the old history became unreachable and HEAD was re-rooted on a tree that already contained the damage. `nightly-backup.sh`'s pre-commit gate does not help — it only guards the nightly job. **Recovery is still possible because the old `.git` pack (593 MB) survives**: the pre-write commit was recovered via `--batch-all-objects` + unreachable filtering.
