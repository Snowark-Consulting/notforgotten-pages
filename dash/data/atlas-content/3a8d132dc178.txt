## 1. SMS Service Interface Design

### 1.1 Architecture Principle

The SMS Service is a **provider-agnostic abstraction layer**. Twilio is the Phase 1 carrier. The interface is designed so that swapping to a different SMS provider requires zero changes to business logic, Decision Engine, or Airtable integration. Only the provider implementation module is replaced.

```
Decision Engine  →  SMSService (interface)  →  TwilioSMSService (Phase 1)
                                              →  [Future: Telstra, Vonage, etc.]
```

### 1.2 Interface Definition

The SMSService exposes 9 functions. All are synchronous. All return structured result objects. None have side effects beyond their documented scope.

```
SMSService Interface
═══════════════════

┌─────────────────────────────────────────────────────────────────────┐
│ FUNCTION                 │ PURPOSE                                  │
├─────────────────────────────────────────────────────────────────────┤
│ send()                   │ Send an outbound SMS. Returns message    │
│                          │ ID, segment count, status.               │
│                          │                                          │
│ receive()                │ Process an inbound SMS webhook. Returns  │
│                          │ parsed message with sender, body, time.  │
│                          │                                          │
│ validate_number()        │ Validate phone number: type (mobile/     │
│                          │ landline/VOIP), carrier, country,        │
│                          │ reachability.                            │
│                          │                                          │
│ check_delivery_status()  │ Poll delivery status for a sent message. │
│                          │ Returns: queued/sent/delivered/failed/   │
│                          │ undelivered.                             │
│                          │                                          │
│ check_consent()          │ Query Airtable for consent tier, opt-out │
│                          │ status, and deliverability. Returns      │
│                          │ ConsentResult with tier and flags.       │
│                          │                                          │
│ log_to_crm()             │ Write SMS activity to Airtable Messages  │
│                          │ table with all SMS-specific metadata.    │
│                          │                                          │
│ handle_opt_out()         │ Process STOP/UNSUBSCRIBE. Mark Airtable  │
│                          │ opt-out flag. Log to Opt-Out register.   │
│                          │ Send confirmation SMS.                   │
│                          │                                          │
│ queue_for_quiet_hours()  │ If current time is within quiet hours,   │
│                          │ queue message for 7:01 AM delivery.      │
│                          │                                          │
│ check_duplicate()        │ Prevent double-sends. Check Airtable for │
│                          │ same purpose + recipient within 60s.    │
└─────────────────────────────────────────────────────────────────────┘
```

## 2. Airtable Schema Recommendations

### 2.1 Current State Assessment

The existing schema already has partial SMS awareness. The Messages table has `Channel` with "Email" and "SMS" options, and `Direction` with "Outbound", "Inbound", and "Tradie SMS". The Prospects table has a `Mobile` field. This is a starting point — it means SMS data has always been part of the data model, just never operationalised.

**What's missing:** Consent tracking, opt-out enforcement, delivery status, frequency tracking, quiet hours support, conversation threading. All of these are required before SMS can be sent safely.

### 2.2 New Fields Required — Prospects Table

| # | Field Name | Type | Options / Format | Rationale |
|---|---|---|---|---|
| 1 | `SMS Consent Tier` | Single select | T0, T1, T2, T3, T4 | Core consent classification. Default: T0. Every SMS send gates on this field. |
| 2 | `SMS Consent Source` | Single line text | Free text | Audit trail: how consent was obtained. "Client onboarding", "Prospect request", "Delegated: Client Name", etc. |
| 3 | `SMS Consent Date` | Date | YYYY-MM-DD | When consent was established. Used for re-verification on dormant records. |
| 4 | `SMS Opted Out` | Checkbox | Boolean | Permanent opt-out flag. Once True, never reset without explicit re-opt-in. Takes precedence over consent tier. |
| 5 | `SMS Opt-Out Date` | Date | YYYY-MM-DD | When opt-out occurred. For audit trail. |
| 6 | `SMS Opt-Out Reason` | Single line text | Free text | Trigger word that caused opt-out (e.g. "STOP"). |
| 7 | `SMS Deliverable` | Checkbox | Boolean | Number validated as mobile and reachable. Updated by validate_number(). Re-checked every 90 days. |
| 8 | `SMS Last Validated` | Date | YYYY-MM-DD | When validate_number() last ran successfully. |
| 9 | `SMS Timezone` | Single select | Australia/Adelaide, Australia/Sydney, Australia/Melbourne, Australia/Brisbane, Australia/Perth, Australia/Darwin, Australia/Hobart | For quiet hours enforcement. Default: Australia/Adelaide. |
| 10 | `Preferred Communication Channel` | Single select | Email, SMS, Both | Client/prospect preference. Advisory, not binding (consent tier is binding). |
| 11 | `Last SMS Sent` | DateTime | ISO 8601 | Frequency cap enforcement and duplicate prevention. |
| 12 | `SMS Message Count` | Number | Integer | Lifetime SMS count for this recipient. For reporting. |

**Total new Prospect fields: 12**

### 2.3 New Fields Required — Messages Table

| # | Field Name | Type | Options / Format | Rationale |
|---|---|---|---|---|
| 1 | `SMS Segment Count` | Number | Integer (1-10) | Number of SMS segments sent. Used for cost tracking and quality (target: 1). |
| 2 | `SMS Delivery Status` | Single select | Queued, Sent, Delivered, Failed, Undelivered | Real-time delivery tracking. Updated by status callback webhook. |
| 3 | `SMS Message SID` | Single line text | Free text | Provider message ID (Twilio: SMxxx). For delivery status lookups. |
| 4 | `SMS Opt-Out Triggered` | Checkbox | Boolean | Did this inbound message trigger an opt-out? For audit trail. |
| 5 | `Quiet Hours Queued` | Checkbox | Boolean | Was this message queued and sent at 7am? For reporting. |
| 6 | `SMS Delivery Error` | Single line text | Free text | Error message if delivery failed. From Twilio error codes. |

**Total new Message fields: 6**
**Existing Message fields that already serve SMS:** `Channel` (SMS), `Direction` (Inbound/Outbound/Tradie SMS), `Body`, `Message purpose`

### 2.4 New Table Required — SMS Consent Log

**Purpose:** Immutable audit trail of every consent state change. Separate from Messages because consent changes are not messages — they are administrative events.

**Table name:** `SMS Consent Log`

| # | Field Name | Type | Options / Format |
|---|---|---|---|
| 1 | `Prospect` | Link to Prospects | Required |
| 2 | `Client` | Link to Clients | Optional (if consent is delegated from a client) |
| 3 | `Event Type` | Single select | Consent granted, Consent upgraded, Consent degraded, Consent expired, Opt-out, Number validated, Number invalidated |
| 4 | `Tier Before` | Single select | T0, T1, T2, T3, T4 |
| 5 | `Tier After` | Single select | T0, T1, T2, T3, T4 |
| 6 | `Event Source` | Single line text | How the event was triggered: "STOP received", "Client onboarding", "Manual override by James", etc. |
| 7 | `Timestamp` | DateTime | Auto-populated |
| 8 | `Notes` | Long text | Context: the message that triggered opt-out, the consent mechanism, etc. |

### 2.5 Schema Changes — What NOT To Change

The existing `Mobile` field in Prospects and Clients is sufficient for phone number storage. Airtable's `phoneNumber` type already handles formatting and validation. Adding a separate "SMS-specific" phone field would create synchronisation problems.

The existing `Channel` and `Direction` fields in Messages already support SMS. The values "SMS" (Channel) and "Tradie SMS" (Direction) are already in the option lists. No changes needed.

### 2.6 Recommendation Summary

| Action | Table | Details |
|---|---|---|
| **Add 12 fields** | Prospects | SMS Consent Tier through SMS Message Count (see list above) |
| **Add 6 fields** | Messages | SMS Segment Count through SMS Delivery Error (see list above) |
| **Create new table** | SMS Consent Log | 8 fields for consent audit trail |
| **No changes** | Clients | Existing Mobile field is sufficient |
| **No changes** | Quotes | Existing Customer mobile field is sufficient |
| **No changes to existing fields** | Messages | Channel and Direction already support SMS |

**Do not make any schema changes until James reviews and approves these recommendations.** This document is the design. Schema changes are implementation.

## 3. Decision Engine Design

### 3.1 Purpose

The Decision Engine answers four questions for every communication Atlas needs to send:

1. **Should Atlas send an SMS?** — Is this message appropriate for SMS, and do all the gates pass?
2. **Should Atlas send an email?** — Is email the right channel for this message?
3. **Should Atlas create a phone task for James?** — Is human intervention required?
4. **Should Atlas wait?** — Is now the wrong time for any channel?

### 3.2 Decision Engine Architecture

```
                         ┌──────────────────────┐
                         │   ATLAS NEEDS TO     │
                         │   COMMUNICATE        │
                         └──────────┬───────────┘
                                    │
                         ┌──────────▼───────────┐
                         │  ROUTE BY CONTEXT     │
                         │  ┌─────────────────┐  │
                         │  │ Recipient type:  │  │
                         │  │ Client / Prospect│  │
                         │  │ / Customer /     │  │
                         │  │ Unknown          │  │
                         │  └────────┬────────┘  │
                         └───────────┼───────────┘
                                     │
              ┌──────────────────────┼──────────────────────┐
              │                      │                      │
    ┌─────────▼─────────┐  ┌────────▼────────┐  ┌─────────▼─────────┐
    │   SMS GATE CHECK  │  │  EMAIL GATE     │  │  PHONE TASK       │
    │                   │  │  CHECK          │  │  CHECK            │
    │ 1. Consent tier   │  │                 │  │                   │
    │ 2. Not opted out  │  │ 1. Email exists │  │ 1. Urgency level  │
```

### 3.3 SMS Gate — Full Decision Flow

This is the definitive check sequence. It fires before every SMS send. A single failure blocks the send.

```
SMS_SEND_DECISION(recipient, message_body, purpose):
    ┌──────────────────────────────────────────────────┐
    │ GATE 1: RECIPIENT EXISTS                         │
    │ Query Airtable Prospects + Clients by phone      │
    │   Found? → Continue                              │
    │   Not Found? → BLOCK. Unknown recipient.          │
    │   Multiple? → BLOCK. Ambiguous recipient.         │
    │   Log attempt. Flag for James.                   │
    └──────────────────────────────────────────────────┘
                         │ PASS
    ┌──────────────────────────────────────────────────┐
    │ GATE 2: CONSENT TIER                             │
    │ Read SMS Consent Tier from Airtable              │
    │   Tier >= MINIMUM_TIER[purpose]? → Continue      │
    │   Tier too low? → BLOCK. Insufficient consent.   │
    │   Tier = T0? → BLOCK. No consent on file.        │
    └──────────────────────────────────────────────────┘
                         │ PASS
    ┌──────────────────────────────────────────────────┐
    │ GATE 3: NOT OPTED OUT                            │
    │ Read SMS Opted Out from Airtable                 │
    │   False? → Continue                              │
    │   True? → BLOCK. Permanent. Never retry.         │
    │   Log attempt with timestamp.                    │
    └──────────────────────────────────────────────────┘
                         │ PASS
    ┌──────────────────────────────────────────────────┐
    │ GATE 4: NUMBER VALID                             │
    │ Check SMS Deliverable flag in Airtable           │
    │   True and validated < 90 days? → Continue       │
    │   False or expired? → Run validate_number()      │
    │     Valid → Update flag, continue                │
    │     Invalid → BLOCK. Flag for review.            │
    └──────────────────────────────────────────────────┘
                         │ PASS
    ┌──────────────────────────────────────────────────┐
    │ GATE 5: NOT QUIET HOURS                          │
    │ Get current time in recipient's timezone         │
    │   7:00 AM ≤ time < 9:00 PM? → Continue           │
    │   Otherwise → QUEUE for 7:01 AM.                 │
    │   (queue_for_quiet_hours() handles this)         │
    └──────────────────────────────────────────────────┘
                         │ PASS
    ┌──────────────────────────────────────────────────┐
    │ GATE 6: FREQUENCY CAP                            │
    │ Count SMS to this recipient today (Airtable)     │
    │   Under daily cap? → Continue                    │
    │   Exceeded? → BLOCK or QUEUE for tomorrow.       │
    │   Caps: Client=3/day, Prospect=1/day,            │
    │         Customer=embedded in sequence cadence    │
    └──────────────────────────────────────────────────┘
                         │ PASS
    ┌──────────────────────────────────────────────────┐
    │ GATE 7: NOT DUPLICATE                            │
    │ Search Airtable Messages for same purpose +      │
    │ same recipient within last 60 seconds            │
    │   No duplicate? → Continue                       │
    │   Duplicate? → BLOCK. Idempotency protection.    │
    └──────────────────────────────────────────────────┘
                         │ PASS
    ┌──────────────────────────────────────────────────┐
    │ GATE 8: SMS VOICE REVIEW (7-point)               │
    │ Run the 7-point checklist on message_body:       │
    │   1. Fits in one segment (≤160 chars)?           │
    │   2. Lead is the news (first 40 chars)?          │
    │   3. No bullshit?                                │
    │   4. No exaggerated claims?                      │
    │   5. Reads naturally aloud?                      │
    │   6. Passes coffee test?                         │
    │   7. Actionable or informative?                  │
    │   All 7 pass? → SEND                            │
    │   Any fail? → REWRITE. Retry Gate 8.            │
    │   2 rewrites fail? → ESCALATE to James.          │
    └──────────────────────────────────────────────────┘
                         │ SEND
                    ┌────▼────┐
                    │  SEND   │
                    │  SMS    │
                    └────┬────┘
                         │
    ┌──────────────────────────────────────────────────┐
    │ POST-SEND: LOG TO CRM                            │
    │ log_to_crm() with all SMS metadata               │
    │ Update Last SMS Sent timestamp                   │
    │ Increment SMS Message Count                      │
    └──────────────────────────────────────────────────┘
```

### 3.4 Channel Selection Matrix

When Atlas needs to send a communication, the Decision Engine routes by message type:

| Message Type | Primary Channel | SMS If | Email If | Phone Task If |
|---|---|---|---|---|
| **Cold outreach** | Email | Never (blocked) | Always | Never |
| **Follow-up (Email 2-4)** | Email | Never (no consent) | Always | Never |
| **Quote reply alert** | SMS first | Consent T1+, not opted out, not quiet hours | Always (dual-send for audit trail) | Never |
| **Quote accepted** | SMS first | Consent T1+, valid number | Always | Never |
| **Daily summary** | SMS (end of day) | Consent T1+ | Optional (user preference) | Never |
| **Monthly digest** | Email primary, SMS supplement | Consent T1+ | Always | Never |
| **System alert (SL3+)** | SMS + Email | Consent T1+, all hours (override quiet hours) | Always | SL4 only |
| **Meeting reminder** | SMS | Consent T2+ | Email backup | Never |
| **Post-call follow-up** | SMS + Email | Consent T2+ | Always | Never |
| **Customer follow-up** | Email primary, SMS supplement | Consent T3+ | Always | Never |
| **Complaint received** | Never SMS | Never | Flag to James | **Always — escalate immediately** |
| **Legal/regulatory** | Never SMS | Never | Flag to James | **Always — escalate immediately** |
| **Opt-out confirmation** | SMS | Always (compliance) | Never | Never |

### 3.5 Escalation to Phone Task

The Decision Engine creates a phone task for James when:

| Trigger | Rationale |
|---|---|
| SMS reply contains complaint or negative sentiment | Do not handle via text. Human conversation required. |
| Client opts out of SMS | Churn risk signal. James should understand why. |
| NFS client's customer opts out and the client has 3+ opt-outs | Pattern problem. Client may not be obtaining consent properly. |
| SMS delivery failure rate > 10% for a single recipient | Number may be wrong. James may have an alternate contact. |
| Two Voice Review rewrites fail | The message content needs human judgment. |
| Any communication where Trust Test produces doubt | If Atlas isn't sure, James decides. |

**Phone task format (Airtable task record):**

```
Priority: High / Medium / Low
Subject: "SMS escalation — [trigger type]"
Context: Linked prospect/client, last 3 messages, reason for escalation
Recommended action: What Atlas would do if it could decide
```

## 4. Unified Conversation Timeline

### 4.1 Design Principle

Every interaction with a prospect, client, or customer should appear in a single chronological timeline, regardless of channel. Email, SMS, and phone activity are different transports for the same relationship. The timeline reflects that.

### 4.2 Data Source

The Messages table is already the single source of truth for all communications. It already supports:
- `Channel`: Email, SMS
- `Direction`: Outbound, Inbound, Tradie SMS
- Timestamps via `Sent at` / created time
- Body content
- Prospect linkage

The unified timeline is a **view** over the Messages table, not a new data store.

### 4.3 Timeline Entry Schema

Every entry in the unified timeline — regardless of channel — has this structure:

```json
{
  "timestamp": "2026-07-27T14:30:00+09:30",
  "channel": "sms | email | phone",
  "direction": "outbound | inbound",
  "actor": "Atlas | James | Prospect Name | Customer Name",
  "content_preview": "First 80 characters of body...",
  "purpose": "Quote reply alert | Follow-up | etc.",
  "status": "delivered | sent | failed | queued",
  "message_id": "Airtable record ID",
  "conversation_thread": "quote-127 | outreach-sequence-abc | general"
}
```

### 4.5 Implementation Approach

The unified timeline is a **query pattern**, not a new table:

1. Query Messages table with `filterByFormula={Prospect}='recXXX'`
2. Sort by `Sent at` descending
3. Augment phone entries from a Phone Call Log (simple table: date, duration, notes, linked prospect)
4. Render with channel-specific icons and formatting

**Phone Call Log table (new, minimal):**

| Field | Type | Purpose |
|---|---|---|
| `Prospect` | Link to Prospects | Who was called |
| `Call Date` | DateTime | When call occurred |
| `Direction` | Single select | Outbound, Inbound |
| `Duration` | Number | Minutes |
| `Notes` | Long text | James's call notes |
| `Outcome` | Single select | Connected, Voicemail, No answer, Callback requested |

This table is lightweight. It exists solely to make phone activity visible in the unified timeline. No complex workflow — just a log.

### 4.6 Conversation Threading

Threads group related messages together. A thread is defined by a shared context, not a technical session:

| Thread Type | How Messages Are Grouped |
|---|---|
| **Quote thread** | All messages linked to a specific Quote record (via Messages → Quotes link) |
| **Outreach thread** | All messages in a single Outreach Sequence for a prospect |
| **Support thread** | All messages about a specific issue (manual grouping) |
| **Onboarding thread** | All messages during client onboarding |

Threads are implemented via the existing `Messages` → `Quotes` link field, and the `Outreach Sequence` field on Prospects. No new fields are required for threading — the existing linkages already define the groupings.

## 5. SMS Template Library

### 5.1 Template Structure

Every template has:
- **ID:** Unique identifier
- **Category:** Client notification / Meeting reminder / Customer service / Post-engagement
- **Purpose:** Canonical purpose value (matches Airtable Message purpose)
- **Consent tier required:** Minimum tier to send
- **Template body:** The fixed text with `{variables}`
- **Expected segment count:** Always 1 (≤160 chars)
- **Quiet hours behaviour:** Send / Queue / Override
- **Notes:** When to use, when not to use

### 5.7 Template Usage Rules

1. **Never modify a template's core structure without James approval.** Variables can be populated. Wording is fixed until evidence supports a change.
2. **Always run SMS Voice Review on the populated template**, not just the template skeleton.
3. **Track template performance.** Tag each SMS in Airtable with the template ID. Measure: delivery rate, reply rate, opt-out rate by template.
4. **If a template generates > 1% opt-out rate**, pause it and escalate to James.
5. **Templates are living.** The Campaign Review framework applies: after each month, review template performance and recommend changes.
