# Security, Privacy & Trust Audit — Not Forgotten Systems

**Date:** 25 July 2026
**Auditor:** Atlas (internal audit, external-consultant methodology)
**Scope:** Full platform — infrastructure, secrets, client data, privacy, AI risk, email, access control, monitoring, compliance
**Classification:** Confidential

---

## Executive Summary

Not Forgotten Systems is a two-month-old startup handling real client data (quotes, customer details, business intelligence) on behalf of trade businesses. The platform is operational and functioning, but security has not been systematically addressed.

**This is expected for a company this young** — no criticism implied. The purpose of this audit is to identify risks before they become incidents, and to build security into the platform as it scales.

### Scores

| Score | Rating | Explanation |
|---|---|---|
| **Security Score** | **41/100** | Critical credential exposures. No firewall, no intrusion detection, world-readable secrets. Core infrastructure is unprotected. |
| **Privacy Score** | **35/100** | Client PII stored without formal policy. No consent framework, no retention policy, no deletion process. 4GB state.db contains all conversations indefinitely. |
| **Operational Maturity** | **38/100** | Monitoring is reactive. No backup beyond git push. No incident response plan. No regular security review cadence. Hermes 270 commits behind. |

### Bottom Line

The platform works. But a single compromise of this VPS would expose every credential, every client conversation, every quote, and every piece of business intelligence Not Forgotten has ever handled. Six critical findings need immediate attention. The rest can be addressed over the next 1-3 months as the business scales.

**This platform is not ready for enterprise clients or anyone with contractual data-handling requirements.** It is adequate for the current validation phase with small trade businesses, provided the critical items below are addressed within 30 days.

| `GODADDY_API_KEY` | `.env` | Plaintext | Never rotated | High |
| `GODADDY_API_SECRET` | `.env` | Plaintext | Never rotated | High |
| `GA4_SERVICE_ACCOUNT_KEY_B64` | `.env` (×2) | Base64-encoded JSON key | Never rotated | **Critical** |
| `google_token.json` | `/root/.hermes/` | JSON (OAuth refresh) | Auto-refresh | Medium |
| `quotes_token.json` | `/root/.hermes/` | JSON (OAuth refresh) | Auto-refresh | **Critical** (644 perms) |

| `atlas_oauth_pending.json` | `/root/.hermes/` | JSON | Unknown | Low |
| `google_client_secret.json` | `/root/.hermes/` | JSON | Never | Medium |
| Vercel token | `/root/.vercel/auth.json` | JSON | Never | Medium (644 perms) |

### Critical Issues

1. **GitHub PAT embedded in git remote URLs** — `hancockjluke:ghp_bJ...` and `Hardstaff08:ghp_bL...` visible in `git remote -v` output and stored in `/root/.git-credentials`. These tokens appear to have repo scope. Rotate immediately.

2. **GA4 service account key exposed** — During this audit, the base64-encoded service account JSON was output to the terminal and captured in `agent.log`. While base64-encoded, this is reversible encoding, not encryption. The key should be rotated. **This is the first incident — IA-2026-001.**

3. **Duplicate entries** — `GA4_SERVICE_ACCOUNT_KEY_B64` and `GATEWAY_ALLOW_ALL_USERS` appear twice in `.env`. The last occurrence wins (shell behaviour), meaning the first entry is dead but confusing. Could mask a wrong-key situation.

4. **No credential rotation** — No credential has ever been rotated. Some tokens (GitHub PATs) are embedded in remote URLs and cannot be rotated without breaking git operations.

5. **quotes_token.json is world-readable** — Any process on the system can read a live OAuth token granting Gmail access to `quotes@notforgotten.com.au`.

### Recommendations

1. Rotate GitHub PATs immediately (Josh + James). Use fine-grained tokens with minimum scope.
2. Remove PATs from git remote URLs. Use `git credential-store` with file permissions 600.
3. Rotate GA4 service account key (incident IA-2026-001).
4. Deduplicate `.env`.
5. `chmod 600` all credential files.
6. Implement Bitwarden Secrets Manager for long-lived credentials (GA4, API keys).
7. Establish 90-day credential rotation policy.
8. Schedule monthly credential audit.

## 5. AI Risk

### Data Flow Into AI Models

Every API call to DeepSeek or Gemini includes the full conversation context:
- System prompt (SOUL.md — this file, ~800 lines)
- Memory entries (summarised business facts)
- The user's message
- All tool output from the current conversation (Airtable records, email bodies, script output)

### Exposure Vectors

| Vector | Risk | Evidence |
|---|---|---|
| **agent.log** | Captures all tool output including Airtable records with PII, email bodies with full names/phones/amounts | Confirmed — 5MB log with unredacted tool output |
| **state.db** | Contains full conversation history — all messages, all tool calls, all responses, across all sessions | 3.9GB and growing |
| **Request dumps** | Full API request/response pairs with complete prompt context | 25 dump files in sessions/ |
| **API transmission** | Prompts sent to DeepSeek (China) include client context | Every session |
| **Error messages** | Stack traces may include variable values | Minimal risk — Python exceptions are well-structured |

### Safeguard Recommendations

1. **PII redaction middleware** — Before tool output enters the conversation context, strip phone numbers, email addresses (when not operationally needed), and physical addresses. This protects logs, state.db, and model prompts.

2. **AI provider risk assessment** — Evaluate whether DeepSeek (China-based) is appropriate for handling client data. Consider whether to route client-data workflows exclusively through Gemini (US-based, existing DPA).

3. **state.db retention** — Implement 90-day rolling retention. Current indefinite storage creates an accumulating privacy liability.

4. **Log-level control** — Add a `--sensitive` flag to scripts that suppresses PII from tool output. Never log full email bodies or Airtable records at INFO level.

5. **Prompt boundary markers** — Consider whether client-specific context can be summarised rather than included verbatim in prompts. The current system includes full names, business names, and quote values directly in tool output that enters the model context.

### Incident IA-2026-001 (This Audit)

During this audit, the GA4 service account private key (base64-encoded) was output to the terminal and captured in `agent.log`. While base64 is encoding, not encryption, the key material was exposed in logs and session storage.

**Action required:** Rotate GA4 key. Review `agent.log` and `state.db` for the exposed key material. Consider this a controlled finding — the audit was designed to find this kind of exposure.

### D. Methodology

This audit was performed by Atlas acting as an external security consultant. Methodology:

1. **Reconnaissance** — Enumerate all system components, services, ports, users
2. **Configuration review** — Inspect all configuration files, environment variables, permissions
3. **Data flow mapping** — Trace personal information from intake to storage to processing to output
4. **Credential audit** — Inventory every credential, check storage, rotation, exposure
5. **External verification** — DNS records, TLS certificate, email authentication
6. **Gap analysis** — Compare against Australian Privacy Principles and security best practices

**Limitations:** This audit did not perform penetration testing, vulnerability scanning, or code review. It assessed configuration, not implementation security. The AI model supply chain (DeepSeek API) was assessed for privacy risk but not for model security.
