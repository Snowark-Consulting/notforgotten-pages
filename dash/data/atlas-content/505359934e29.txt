## The resilience argument that changed since 24 Aug

The `wakeAgent` gate was deployed 2026-08-18. Empty ticks emit `{"wakeAgent": false}` and the agent is skipped — **$0 idle**. That was a cost win, and it also changed the failure signature:

| Before the gate | After the gate |
|---|---|
| A provider outage caused repeated cron error spam into the alert channel | An outage surfaces as **missed pulses** — quiet, with no alert at all |

The original containment goal from the Jul-24 decision (stop the spam) is now met by the gate, not by a fallback chain. But the same gate **removes the alarm**. A multi-hour DeepSeek outage would now delay `inbox-pulse-phase2` and `quotes-pulse-phase2`. Those are the paths that detect a QPaint customer reply. A silent detection delay is a **service-continuity risk**, which SOUL Principle 13 places above provider loyalty.

This is the substantive new evidence for 24 Sep, and it cuts both ways: the gate solved the noise, and it created a new blind spot that a fallback chain would partially cover.

## Verdict options for review (James decides)

1. **Restore the chain** — add a fallback provider (DeepSeek → alternative) so retry-exhaustion and multi-hour outages fail over automatically. Requires a config write done by script, not `hermes config set`, because list-valued settings must be written as real YAML lists. Consistent with `2026-08-17-deepseek-client-data-approved`, which permits a fallback provider for reliability.
2. **Accept single-provider posture formally** — DeepSeek primary only; `wakeAgent` gate is the containment; outages surface as missed pulses. Would need a compensating control for the blind spot above (for example, a heartbeat that alerts when a pulse has not run for N hours).
3. **Defer again** — no change now. Weakest option available this time: the decision has already been deferred once, and the evidence base has not stood still.

## Questions for the 24 Sep review

1. Is a 21-day clean run, following 27 absorbed transients, enough to treat single-provider as settled?
2. Does the `wakeAgent` gate's silent-failure mode need a heartbeat alert regardless of which option is chosen?
3. If option 1: which provider, given DeepSeek is the approved carrier for client data?
4. Should the config's `'[]'` **string** form be corrected to a real empty list as a standalone hygiene fix, so a future fallback write is not silently ignored?
