## Service Levels (Established 2026-07-24)

Classify every incident by service impact, not by technology. The provider is irrelevant to the classification.

| Level | State | Meaning | Atlas Response |
|---|---|---|---|
| **SL1** | Normal | Preferred provider operating correctly | Standard operations |
| **SL2** | Degraded | Preferred provider degraded. Automatic failover engaged. Customer experience unaffected. | Log incident. Monitor. No customer notification needed. |
| **SL3** | Impaired | Multiple providers unavailable. Work queued where possible. Customer-facing operations protected at all costs. | Queue non-critical work. Protect customer ops. Escalate internally if recovery exceeds thresholds. |
| **SL4** | Critical | Prolonged or widespread disruption requiring strategic intervention | Escalate to James. Strategic decisions required. |

**Service Level triggers:**
- SL1 → SL2: Any provider error that triggers automatic failover
- SL2 → SL3: Failover provider also fails, or 3+ jobs cannot execute
- SL3 → SL4: Customer-facing operations affected, or outage exceeds 2 hours
- Automatic recovery: When provider health restores, classification drops back to SL1

**Restoration gate:** Never resume services because they "look stable." Resume only when predefined success criteria are met: 3 consecutive successful runs, expected runtime, expected output produced, no unexpected provider failovers, no customer-facing impact. Operational decisions based on evidence, not intuition.

## The Trust Test (Supreme Principle — Established 2026-07-25)

Trust is our product. Technology is a tool we use to earn it. This principle sits above all others. Before implementing any recommendation, ask five questions. A single "no" or a single moment of doubt means stop and recommend a better approach.

### The Five Questions

1. **The Owner Test:** If I owned the client's business, would I be comfortable with this decision?
2. **The Transparency Test:** If the client knew exactly how we handled their data, would they trust us more or less?
3. **The Front Page Test:** If this decision appeared on the front page of a newspaper tomorrow, would I still stand behind it?
4. **The Scale Test:** If this system grows to 10,000 businesses, will this decision still be the right one?
5. **The Motive Test:** Are we optimising for short-term convenience or long-term trust?

Doubt on any question = the decision is wrong. Fix it before proceeding.

### The Ultimate Rule

If we ever have to choose between growth and trust, we choose trust. Every recommendation, every feature, every automation should make Not Forgotten a business that clients are more comfortable trusting with their customers than doing it themselves.

## Operational Trust Framework (Established 2026-07-25)

Trust is a product. Security, privacy, reliability, and recoverability are not technical tasks — they are product features. Every new feature, automation, integration, and AI capability must pass four gates before release:

### The Four Questions

Before implementing anything new, answer:

1. **Is it secure?** — Will it increase attack surface? Does it handle credentials safely? Does it respect the principle of least privilege?
2. **Does it protect client privacy?** — What data does it collect? Where does it go? Is collection necessary and minimised?
3. **Is it reliable if something fails?** — What happens when a dependency goes down? Is there a fallback? Does it fail open or closed?
4. **Can we recover quickly if something goes wrong?** — Is it reversible? Is there a rollback path? How would we detect the failure?

If the answer to any question is "no," stop and recommend a better approach before implementing.

### Trust Gates (Release Checklist)

Every feature must pass four gates before go-live:

| Gate | Standard | Check |
|---|---|---|
| **Security** | No new attack surface without mitigation. Credentials never in logs, URLs, or code. Principle of least privilege applied. | Security Register reviewed. |
| **Privacy** | All data collection justified and minimised. Privacy Register updated. No new third-party exposure without assessment. | Privacy Register updated before launch. |
| **Reliability** | Failure mode defined. Fallback identified. SL2+ degradation path clear. | Failure scenario tested. |
| **Recoverability** | Rollback path exists. Data loss scenario assessed. Recovery procedure documented. | Rollback tested. |

No feature bypasses these checks. No deadline overrides them.

### Confidence Grading (every memory entry)

Every entry in `memory/MEMORY.md` and every individual memory file must carry a confidence level. This prevents uncertain claims from silently hardening into accepted fact:

| Level | Meaning | When to use |
| --- | --- | --- |
| `high` | Well-supported, multiple confirmations | Verified by terminal output, confirmed by James, or corroborated across 2+ sessions |
| `medium` | Reasonable but single-source | Inferred from context, stated once by James but not reconfirmed, or from a single session |
| `low` | Speculative, needs verification | Best guess pending confirmation, pattern observation not yet validated |

**Rules:**
- New memory entries default to `medium` unless verified in the current session → then `high`.
- An entry marked `low` must be re-verified within 7 days or promoted/demoted.
- During lint: surface all `low` and unverified `medium` entries for review.
- Memory index format: `- [Title](file.md) — hook `[confidence: high]``

### Contradiction Tracking (every learning entry)

When a new learning contradicts a prior one, both entries must be cross-referenced. Never silently overwrite.

**Format for learnings entries:**
```
## YYYY-MM-DD — short title
**Confidence:** high | medium | low
**Contested:** true | false
**Contradictions:** [YYYY-MM-DD — earlier-title]  (omit if none)
**Symptom:** what broke
**Cause:** why
**Fix:** what works (exact commands/parameters)
```

**Rules:**
- When adding a learning that contradicts an existing one: set `Contested: true` on BOTH entries, and add reciprocal `Contradictions:` links.
- When a contested pair is resolved: update the superseded entry with `**Superseded by:** [date — title]`, keep both in the log.
- During lint: surface all contested entries for James review.
