# state.db stopped persisting sessions at 09:45 ACST — 6 sessions and a day of intake transcripts are unrecorded

**Confidence:** high
**Contested:** false

## Symptom

Found while gathering the 18 Sep daily note. `session_search()` returned:

```
Session database not available: OperationalError: disk I/O error
(state.db may be on NFS/SMB/FUSE/ZFS — see https://www.sqlite.org/wal.html)
```

A direct read-only query confirmed the database is readable but has simply stopped receiving rows.

## Evidence

| max(`sessions.started_at`) | **2026-09-18 00:14:57 UTC = 09:44:57 ACST** |

| `PRAGMA quick_check` | **ok** |

## Impact

- The QPaint #43195 intake transcript — including the reasoning behind the weekend-guard
  divergence — is not persisted anywhere except its own learning file and the Airtable record.
- `session_search` is unusable. Dream, the nightly consolidation, and session-librarian all read it.
- Any job that derives counts, cost or activity from `state.db` under-reports for the period.
- `logs/tool-calls.jsonl`, `cron/output/` and `cron/executions.db` are separate stores and are
  **still live** — which is why the failure is easy to miss: the system looks healthy from every
  other angle.

## What was NOT done

Nothing was repaired. `state.db` is Hermes core infrastructure; the failure is not a disk-space or
corruption case (`quick_check` is ok), so there is no unambiguously safe fix, and rule 10 stops
production — including infrastructure changes — when an assumption is unverified. No `VACUUM`, no
`REINDEX`, no file surgery, no restart. Raised as rec `consolidation-state-db-persistence-stop` and
logged in `Agent/Infrastructure.md` for Winston/Josh.

## Lessons

- **A liveness signal is not a persistence signal.** Cron outputs, `executions.db` and
  `tool-calls.jsonl` all kept working normally while `state.db` silently stopped accepting rows.
  Only a direct max-timestamp query surfaces it.
- **`session_search` failing is a symptom, not the fault.** Read the error as "the session database
  is not available", then verify persistence directly rather than retrying the tool.
- **Do not diagnose a 4-day-old gateway as the cause.** The gateway uptime was checked precisely to
  rule out a restart, and it ruled one out — record what you ruled out, not just what you found.
- **Column names in `state.db` are not what the docs imply** — `sessions` has `started_at` and
  `last_activity_at`, and has NO `session_id`, `created_at` or `updated_at`. Two ad-hoc queries
  failed on exactly those names tonight (see rec `dream-err-state-db-session-id-column`).
- **There is no `sqlite3` CLI on this box.** Use `python3` with
  `sqlite3.connect('file:state.db?mode=ro', uri=True)`.
