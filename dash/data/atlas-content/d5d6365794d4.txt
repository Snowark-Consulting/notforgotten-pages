## 2026-08-18 — Overdue-follow-up miss (root cause) + Outreach Notes overwrite

**Symptom:** 6 QPaint records with Next Touchpoint Date ≤ 18 Aug were missed in the Monday deep-dive. 3 had genuine overdue SENDS (Jesse Zhao Email 3, Peter Reilly Email 2, Shalender Hingorani Email 1), 2 were MONITOR reviews, 1 was a QPaint reconciliation.

**Cause:** Inherited the "0 overdue follow-ups" claim from the 17 Aug daily note (which was wrong) and bucketed the 6 records as "Atlas-owned MONITOR/WAIT" without checking the NTD field against the actual date. "MONITOR" / "WAIT / REVIEW" are planning labels, NOT evidence the underlying action was completed. This is the same trap the recovery-operations skill warns about ("Next Touchpoint Date is a plan, not evidence").

**Fix:** Always compute overdue by comparing `Next Touchpoint Date` against Adelaide "today" directly, and treat every NTD ≤ today as needing a verified action (send OR review OR reclassification) — never assume "MONITOR" means "done". When the daily note says "0 overdue", verify it against a live NTD scan before trusting it.

**Second symptom:** A PATCH setting `Outreach Notes` to a new string OVERWRITES the entire field (wipes history). Append-only is mandatory.

**Fix:** Always read the current `Outreach Notes` from Airtable, then PATCH with `existing + "\n\n" + new_note`. Never PATCH a bare new-note string. (Restored Carlie Gunn + Alicia Campbell notes after the overwrite.)

## 2026-08-24 — GitHub backup silently broken (two failure modes)

**Confidence:** high
**Contested:** false
**Symptom:** Nightly "backup to GitHub" cron reported "ok" for ~36h but nothing was actually pushed. Repo sat 43 commits ahead of origin/main, and state.db snapshots never reached GitHub at all.

**Cause (two independent bugs):**
1. Stale `http.extraheader` in `.git/config` (Basic auth, token `ghp_bLx`) overrode the correct URL-embedded token (`ghp_bJO` = `SNOWARK_GITHUB_TOKEN`). `git ls-remote origin` returned "Repository not found" even with a valid token, because the extraheader wins over URL credentials.
2. `.gitignore` rule `state/` (un-anchored) matched ANY `state/` directory, including `backups/state/` where the snapshot script writes. `git add backups/state/` silently staged nothing, so the snapshot was never committed or pushed.

**Fix:**
1. Update `http.extraheader` to the working token: `git config http.extraheader "Authorization: Basic $(printf 'hancockjluke:%s' "$SNOWARK_GITHUB_TOKEN" | base64 -w0)"`.
2. Anchor the gitignore rule: `state/` → `/state/` (only ignores the repo-root runtime dir).
3. Add `backups/*.corrupted*` to gitignore (a 1.4GB corrupted DB must never be committed — exceeds GitHub 100MB limit).

## 2026-08-27 — Skill file updated but live cron job prompt not resynced: stale instructions silently override

**Confidence:** high
**Contested:** false
**Symptom:** After updating a skill/reference file (e.g. `cron-prompt.md`), a live cron job kept using the old embedded prompt. A mention/tag directed at the agent was suppressed ~24h because the job's stale prompt said "Josh actor → SILENT" even though the reference file correctly said "Tier 4 action, deliver work."
**Cause:** A cron job's embedded prompt is set at job creation/update time (`hermes cronjob update`), NOT read from the skill file at runtime. Updating the skill file alone never reaches the running job; there is no auto-sync.
**Fix:** After updating any skill file or reference a cron job depends on: (1) update the live job prompt with `hermes cronjob update <job-id>`; (2) keep the on-disk reference updated too; (3) verify divergence is gone with `hermes cronjob list <job-id>` (diff live prompt vs reference); (4) never treat reference files as source of truth for running cron jobs — the job's own prompt is operative.
**Source:** 2026-08-27 — Winston cron job 679ee866e13b; Josh's Asana @mention replied ~24h late. Full detail: `learnings/cards/cron.md`. Indexed by consolidation 2026-08-28.

## 2026-09-11 — Raw Gmail API message resource uses `labelIds`, not `labels`

**Confidence:** high
**Contested:** false
**Symptom:** A post-`modify` verification printed an empty label list (or `UNREAD present: False`) for a message that in fact carried the label — a false negative that made a failed label write look successful. Seen during quotes@ intake #43160: `msg.get('labels')` returned missing/`[]` before and after, while `msg.get('labelIds')` showed `['Label_135578373843577379','CATEGORY_UPDATES']`.
**Cause:** The raw Gmail API message resource field is `labelIds`. The key `labels` only exists in `google_api.py`'s normalised JSON output, which maps `labelIds` → `labels`. Mixing the two shapes reads a key that is not there.

## 2026-09-11 — Shell `date` is UTC on this host; hand-labelled ACST timestamps are wrong

**Confidence:** high
**Contested:** false
**Symptom:** An Outreach Notes prefix was hand-written as `[2026-09-11 06:47 ACST]` while the actual local time was 06:44 ACST. The system `date` reads ~21:1x UTC while the injected Adelaide time reads ~06:4x the next day — a 9h30m divergence that is easy to write past without noticing.
**Cause:** The orgo host runs with TZ=UTC. `date '+%Y-%m-%d %H:%M ACST'` prints the UTC clock with the literal string "ACST" appended — it does NOT convert. Any persisted timestamp built that way is silently 9h30m off.
