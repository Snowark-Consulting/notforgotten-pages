### 2026-10-04
- **A stray `/tmp/inspect.py` shadowed the stdlib and broke every Python script run from `/tmp`.** Python puts the script's own directory at `sys.path[0]`, so running from `/tmp` imported a leftover fencing scraper instead of stdlib `inspect`; the symptom was `AttributeError: module 'inspect' has no attribute 'signature'` from `typing_extensions` with ~2 KB of foreign scrape output above it. Directory-scoped, so it silently broke **every** agent's `/tmp` scripts on the shared box. Rule: write scratch scripts to `~/.hermes/scripts/`, never `/tmp`; a traceback naming a stdlib module that "has no attribute X" is a shadowing signature — check `sys.path[0]`. Contained by reversible rename to `/tmp/DISABLED_inspect.py.bak`. → `knowledge/website-intelligence-standard.md` (script pitfall)
- **james-pulse: a QPaint-internal reply on a live HELD record is an escalation ANSWER, not generic FYI.** Where a live QPaint Pipeline record sits HELD awaiting a QPaint answer, the answer necessarily lands in james@ (the escalation travels james@ → QPaint). Treating it as no-action FYI leaves the record stale and the hold standing on an already-answered question. Record the decision verbatim in `Outreach Notes`, rewrite `First Action` to ANSWER RECEIVED, lift the hold / set the NTD, append the message ID, verify by read-back, surface. "FYI, no action" applies only when no live record is awaiting the answer.
- **Pitfall 54 in a second host: a Python-generated log timestamp labelled ACDT while the Outreach Notes prefix was correct.** The host clock is UTC; appending the literal string "ACDT" produces a plausible-looking line that is 9h30m wrong. Only comparison against the injected current-time line exposes it. Always compute with an explicit `TZ=Australia/Adelaide date` call.
- **The DST fix hit the instance, not the class: a hardcoded +09:30 offset staled 60 scripts, including the send gateway.** `timezone(timedelta(hours=9, minutes=30))` turns over at 02:00 on the ACST→ACDT transition; the morning's fix went to `overnight-hq-regen.py`, and the same pattern was then found in `scripts/ga4-intel.py` (emitting a stamp an hour stale, and able to compute the wrong 7-day window) plus 60 further hits under `scripts/`/`bin/` — including the sole outbound gateway `scripts/canonical-send.py`, where a 00:00–01:00 ACDT send is *dated the previous day* and so feeds the weekend-send gate. Fix applied to the two GA4 scripts via `ZoneInfo("Australia/Adelaide")`; gateway left to the infra owner. Rule: a DST transition invalidates every hardcoded offset at once, so **sweep for `timedelta(hours=9` when one is found** — the existence of the rule is what makes it look solved. → `learnings/cards/python.md`

## 2026-10-02 — A daylight-saving transition fires daily cron jobs an hour early, and some of them twice

**Confidence:** high (reproduced by calling the scheduler's own next-run function across the real job set)

The attached offset is the *correct* post-transition `+10:30`, so the output looks right until the wall clock is compared to the expression. Inter-job ordering is preserved. Worse, the affected jobs then fire a **second** time: re-arming from the early fire lands on the intended time the same day (`06:30` → `07:30`), so the QPaint job, the overnight report, the nightly memory consolidation, the nightly backup and the Prepare-Ahead Clock all run twice on 4 Oct. From Monday the computation is correct again — the defect is single-occurrence and transition-day only.
**Cause:** the stored absolute instant and `now` carry different UTC offsets across the boundary, so the recompute derives the local time from the wrong offset. `cron/jobs.py:3254-3268` documents an *accepted* trade-off for a **skip** ("a DST boundary that satisfies all four conditions will recompute and thus SKIP the pending occurrence, no catch-up"), but the observed result is recompute-then-**double-fire** — the same root cause seen from the other side, and on the side the comment did not consider.

(3) **Do not hand-edit `next_run_at` in `jobs.json` from inside a cron run** to correct this — intervening in the scheduler's stored state is a higher risk than the defect. (4) **One-shot jobs are exempt** — the offset-repair path is guarded on `kind == "cron"` and a one-shot's `run_at` is an absolute instant (verified for the CUST2 pilot's Mon 5 Oct 09:00 job). (5) **The customer's clock is a separate decision from the scheduler's bug:** Adelaide shifts and Queensland does not, so from Mon 5 Oct the QPaint Daily Attention delivers at **07:00 Brisbane instead of 08:00** — an unowned, silent change to the customer's experience that persists to April 2027. **Applied:** `learnings/2026-10-02-dst-transition-cron-double-fire.md` (full record); `knowledge/qpaint-review-pack-2026-10-03-05.md` §4 (founder-facing). This is the same class as the field-name false-zero trap on the QPaint table (the empty result that meant "wrong field", not "no data"): both are cases where the shape of the output, not the data, produced the conclusion.
**Rule:** never quote a count that came from reading a print. Aggregate in the script and emit the aggregate as its own explicit line (`print("counts by date:", dict(counter))`). If a scan was run through `head`/`tail`, re-run it **bare** before any number from it is written into a pack, a decision, or a report. Where a set is large enough to truncate, print the total **before** the per-record detail, so the first thing lost is detail, never the total.
**Source:** Prepare-Ahead Clock, 2026-10-06 22:00 ACDT.
