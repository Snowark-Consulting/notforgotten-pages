Customer Journey Data Model v3

Separating Verified Reality from Planned Intention — INC-2026-08-07-003

ARCHITECTURAL PRINCIPLE: Reality and intention must never share the same field. A future action cannot become historical fact simply because it was scheduled.

Current Problem (v2 Schema)

The Current Stage field carries two conflicting meanings:

RecordCurrent Stage saysActual meaningGmail proves
Jesse Zhao "Email 2" "Email 2 is the next planned action" Only Email 1 was ever sent
Laurie Wright "Email 2" "Email 2 is what we intend to do" Only Email 1 was ever sent

This conflation caused the 32-customer incident: Airtable reported "Email 2" as if it had happened, but it was only planned.

Proposed v3 Schema

Field Changes Summary

v2 Fieldv3 Treatmentv3 FieldMeaning
Current Stage CHANGE Verified Stage What has actually happened — independently verified. Options: New | Email 1 Sent | Email 2 Sent | Email 3 Sent | Email 4 Sent | Email 5 Sent | Customer Replied | Engaged | Won | Lost | Deferred
— NEW Next Action What Not Forgotten currently intends to do. Options: Send Email 1 | Send Email 2 | Send Email 3 | Send Email 4 | Send Email 5 | Reply to Customer | Escalate to Client | Call Customer | Wait / Monitor | Close — Lost | Close — Won | Investigate | No Action
— NEW Next Action Status State of the planned action: Planned | Due | Awaiting Approval | Blocked | Completed | Cancelled
Next Touchpoint Date CHANGE Next Action Date When the planned action should be considered. Renamed for clarity — "touchpoint" implied communication had occurred.
Recovery Status KEEP Recovery Status High-level recovery state: Not Contacted | Contacted | Replied | Engaged | Won | Lost. Remains useful for reporting.
Last Contacted KEEP Last Verified Contact Date of last independently verified communication. Renamed for clarity. ONLY updated via state-transition.py.
First Action REMOVE — Superseded by Next Action. Free-text action descriptions are too ambiguous.
Action Reason REMOVE — Superseded by Next Action + Outreach Notes context.
Outreach Notes KEEP Journey Log Chronological relationship timeline. Renamed to reflect its purpose: a permanent narrative of the customer relationship, not just outreach activity.
— NEW Last Verified Gmail ID The most recent independently verified Gmail message ID for this customer. The invariant anchor. Blank = no proven communication.

Key: "Email 2 Sent" only appears in Verified Stage AFTER Gmail independently proves it. Between planning and sending, the stage stays at "Email 1 Sent." The Next Action field carries the intention. The Verified Stage carries the reality.

Enforcement Rules

RuleEnforcement
Verified Stage can only advance via state-transition.py Architectural: only one function writes this field. Every other path is blocked.
Verified Stage requires Last Verified Gmail ID Code: advance_stage() rejects empty Gmail ID at Gate 1.
Next Action can be set independently of Verified Stage Allowed: planning does not change reality. Analysis scripts may set Next Action without Gmail verification.
Next Action Status transitions are constrained Planned → Due → Completed OR Cancelled. No other transitions without manual override.
Headquarters reports Verified Stage, not Next Action Dashboard, Decision Board, CEO Brief — all report what has happened, not what is planned.
Reconciliation watchdog compares Verified Stage against Gmail Daily: any Verified Stage without a matching Gmail count = BLOCKING issue.

Migration Plan

Scaling Beyond QPaint

The model is client-agnostic:

  • Verified Stage — universal. Every client's customers go through a journey. The stages are client-configurable but the invariant is the same: only advance with verified evidence.
  • Next Action — universal. Every client's customers have a next action. Options are client-configurable.
  • Next Action Status — universal. Planned / Due / Blocked / Completed / Cancelled works for every client.
  • Last Verified Gmail ID — universal. Every client's communication channel produces evidence. Gmail is our current channel; the field name is specific but the pattern generalises.
  • Reconciliation watchdog — universal. Compare verified stage against evidence. Works for any channel.

For future clients, this becomes the default schema at onboarding — not retrofitted after an incident.
